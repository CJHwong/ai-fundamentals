# 2.1 什麼是 Agent

## LLM 會想，Agent 會做

上一章我們知道 LLM 是很強的「思考引擎」，但他只能輸出文字。不能查資料庫、不能寄 email、不能跑程式、不能操作任何外部系統。

Agent 就是把這個思考引擎接上手腳。

一個 Agent 的組成很簡單：

```
Agent = LLM + Tools + Loop
```

- **LLM**：負責理解目標、拆解步驟、做決策
- **Tools**：LLM 可以呼叫的外部能力（API、資料庫、搜尋引擎、shell 指令等）
- **Loop**：Plan → Act → Observe → Reflect 的循環，讓 Agent 可以根據結果調整下一步

## Plan-Act-Reflect 循環

舉一個具體的例子。你跟 Agent 說：「幫我查一下這封 email 的訂單狀態，然後指派給負責人。」

Agent 不會一次把所有事做完。他會進入一個循環：

1. **Plan**：拆解任務。「我需要先分析 email 附件拿到訂單編號，再用編號查訂單，再查負責人，最後建立待辦事項。」
2. **Act**：執行第一步。呼叫附件分析 API，拿到訂單編號。
3. **Observe**：檢查結果。分析成功，訂單編號 = ORD-25080042。
4. **Reflect**：成功了，進入下一步。用這個編號去查訂單詳情。

如果第三步失敗了呢？Agent 會回到 Plan，調整策略再試。

這個循環就是 Agent 跟普通 LLM 呼叫的根本差異。普通的 LLM 呼叫是 one-shot：你問一次，他答一次。Agent 是一個持續的決策迴圈，直到任務完成或確定無法完成。

## Agent 也可以跑 Workflow

一個常見的誤解是：Workflow 跟 Agent 是兩種不同的東西，要選一個用。

其實不是。只要你把流程寫清楚，Agent 完全可以照著固定步驟走。差別在於你怎麼下指令：

- **指令很嚴格**（「先做 A，等 A 完成再做 B，B 完成再做 C」）→ Agent 的行為跟 workflow 一樣，可預測、可控
- **指令很鬆**（「幫我處理這封 email」）→ Agent 自己決定怎麼做，彈性高但不一定每次走一樣的路

所以起步的時候，直接用 Agent 配上清楚的指令來跑你的流程就好。好處是迭代快，改指令就改行為，不用動程式碼。

那什麼時候才需要 hard-coded workflow（像 n8n 這類工具）？當你的流程已經穩定、跑了一陣子確認沒問題之後，可以把不需要 LLM 推理的步驟抽出來用程式跑。目的是省 token 成本，因為每一步經過 LLM 都在燒錢。

簡單說就是一條成熟路徑：

```
用 Agent + 清楚指令跑流程（快速迭代）
  → 流程穩定後，把不需要推理的步驟抽到 hard-coded workflow（省成本）
```

先用 context 跑通，再用 code 優化。

## 「最後的抽象」

回顧軟體發展史：

- **物件導向**：把程式碼結構化
- **微服務**：把系統結構化
- **API**：把服務之間的溝通結構化

但每一層抽象裡，都還是人類在寫邏輯。人類一直都是「商業需求」跟「程式碼」之間的翻譯者。

Agent 改變了這件事。你給 Agent 一個**目標**，而不是一個腳本。他自己決定怎麼達成。

這是軟體史上第一次，我們可以圍繞**意圖**來設計系統，而不是圍繞**邏輯**。

## Quiz

**Q1.** Agent 跟單純的 LLM 呼叫，最關鍵的差異是什麼？

- A) Agent 用的模型比較大
- B) Agent 有 Plan-Act-Reflect 循環，可以根據結果調整
- C) Agent 可以理解中文
- D) Agent 不會產生 hallucination

<details><summary>答案</summary>B。單純的 LLM 呼叫是 one-shot（問一次答一次），Agent 是持續的決策迴圈，可以觀察結果、調整策略再試。</details>

**Q2.** 你要做一個功能：收到客戶 email 後，自動分類並轉給對應的團隊。應該用 Workflow 還是 Agent？

- A) Agent，因為比較先進
- B) Workflow，因為分類完之後的流程是固定的
- C) 兩者都不需要，直接用 LLM 就好
- D) 看心情

<details><summary>答案</summary>B。這個場景中，LLM 只負責分類，後續流程是固定的 if-else 規則。不需要動態決策，用 Workflow 就夠了，更可控、更便宜。</details>
