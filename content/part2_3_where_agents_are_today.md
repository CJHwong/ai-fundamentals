# 2.3 Agent 的現況：能做什麼、還不能做什麼

## Agent 不是萬能的

Agent 補上了 LLM 的不足，但也帶來了自己的問題。搞清楚這些問題，才能在實務上做出對的設計決策。

## 三個尚未解決的問題

### 1. 成本 (Cost)

Agent 的 Plan-Act-Reflect 循環中，每一步都可能需要呼叫一次 LLM。一個複雜任務可能跑十幾輪循環，每一輪都在燒 API credits。

| 使用方式 | 大約成本 |
|---------|---------|
| 單次 LLM 呼叫 | $0.01-0.10 |
| Agent 完成一個多步驟任務 | $0.50-5.00 |
| 企業級 Agent 對話 | $2.00+ |

這代表你不能把 Agent 用在所有事情上。它適合高價值、多步驟的任務，不適合用來回答一個簡單問題。

**趨勢：** 推理成本正在快速下降。同一個時期，不同模型的推理速度差異可以超過 10 倍（例如 o3-pro 約 23 tokens/s，而 Gemini 2.5 Flash 可達數百 tokens/s）。更小但更聰明的模型（如各家的 mini/flash 系列）讓日常任務的成本大幅降低，只在真正需要深度推理時才動用昂貴的大模型。

### 2. 規劃複雜度 (Planning Complexity)

當任務步驟超過 5-6 步，可能的執行路徑會爆炸性成長。Agent 只要一步順序錯了，整個任務就可能失敗。

> 舉例：有個 Agent 負責處理 email，要依序跑四個步驟，每一步的輸出是下一步的輸入。但較小的模型直接跳過等待，同時呼叫四個工具，編造了不存在的參數。

這不完全是模型的問題，也是架構的問題。你可以透過：
- 更好的 prompt 設計來約束執行順序
- 把複雜任務拆成多個小 agent 協作
- 用 workflow 固定關鍵路徑，只在需要判斷的地方讓 agent 介入

另一個容易踩的坑：**給 Agent 太多工具反而會讓它變笨。** 每個工具定義都會佔 context 空間，工具太多會稀釋 attention，讓 Agent 在不該用某個工具的時候去用它。挑選 Agent 需要的工具時，少即是多。

但即使做了這些，長鏈任務的可靠性仍然是 agent 最大的挑戰。

**趨勢：** 更強的 reasoning model（如 o3、Claude Opus）在遵循複雜指令方面明顯進步。而且模型升級有時候比改 prompt 更有效。把模型從一個 120B 參數的模型換到 671B 參數的模型後，幻覺問題直接消失了。更大的模型有更強的能力去處理複雜 context 中的細微差別，不容易在多步驟任務中「跳步」。

### 3. 安全性 (Safety)

Agent 能操作外部系統，這代表它的錯誤不只是「回答錯誤」，而是「做錯事」。

LLM 亂講頂多給你一個錯誤的答案。但 Agent 亂來的話，可能寄出不該寄的 email、刪掉不該刪的資料、或對外部系統做出無法挽回的操作。

單靠 prompt 無法防範所有惡意攻擊（Prompt Injection、Jailbreak）。實務上的做法：

1. **Guardrails**：在 input 進入主 Agent 前，先用一個小模型過濾惡意意圖
2. **限制影響範圍 (Blast Radius)**：不要給 Agent 超出必要的權限。絕對不要讓 Agent 直接寄 email，而是讓它產生草稿，由人類確認後才送出
3. **Human-in-the-Loop (HITL)**：在關鍵決策點設計人類審核機制

> [研究指出](https://blogs.cisco.com/ai/open-model-vulnerability-analysis)，針對主流模型的多輪 jailbreak 攻擊成功率可達 90% 以上。資安的原則是：有 1% 被攻破的風險就算不及格。

## Human-in-the-Loop 不是退讓

HITL 常被誤解成「AI 不夠好才需要人來幫忙」。但其實這是刻意的設計決策：

- AI 負責繁重的工作：分析、搜尋、草擬、分類
- 人類負責最終決策：確認、批准、修正

這種分工結合了 AI 的速度跟人類的判斷力。這不是暫時的妥協，短期內高風險的場景都需要這個機制。

好的 HITL 設計不是讓使用者在對話框裡空等。Agent 應該在背景執行，需要人類確認時再彈出通知或 Widget。使用者的核心任務從「操作」轉變為「驗證」。

### 安全直覺需要時間養成

講一個現實：大部分人剛開始用 Agent 的時候，不會認真對待安全性。正常的學習曲線大概是這樣：

1. 開始用，覺得每次都要確認權限很煩
2. 關掉權限提示，進入「什麼都放行」模式
3. 用久了，慢慢發展出自己的安全直覺

希望在第 2 到第 3 步之間不要出事。

一個幫助建立直覺的思考方式：**你不會把自己的帳號密碼分享給最好的同事吧？但如果你給 Agent 不受限制的存取權限，你做的其實是一樣的事。**

不用一開始就把安全搞得很完美，但至少要意識到風險在哪。隨著你使用 Agent 的經驗越來越多，你會自然發展出「這個權限該不該給」的判斷力。

## 現況總結

| 面向 | 現在 | 趨勢 |
|------|------|------|
| 成本 | 複雜任務仍然昂貴 | 推理成本快速下降 |
| 規劃 | 超過 5-6 步開始不穩定 | 更強的 reasoning model 持續改善 |
| 安全 | 需要 guardrails + HITL | 安全機制正在標準化，但仍不可省略 |
| 適用場景 | 高價值、有明確 tools 的任務 | 隨成本下降，適用範圍持續擴大 |

Agent 正在快速進化，但今天做設計不該建立在「反正以後會更好」的假設上。先用今天可靠的方式做，同時預留升級空間。

## Quiz

**Q1.** 你的 Agent 需要幫客戶發送 email 確認訂單。以下哪個設計最安全？

- A) 讓 Agent 直接寄出 email
- B) 讓 Agent 產生 email 草稿，人類確認後才寄出
- C) 用 prompt 告訴 Agent「不要寄錯」
- D) 用比較貴的模型就不會出錯

<details><summary>答案</summary>B。限制影響範圍（blast radius）是關鍵。Agent 產生草稿，人類做最終確認，這就是 Human-in-the-Loop。</details>

**Q2.** 一個 Agent 在處理 10 步驟的任務時，第 7 步開始出錯。以下哪個做法最不建議？

- A) 換一個更大的模型試試
- B) 把 10 步拆成幾個小 agent 分工
- C) 用 workflow 固定前 6 步，只讓 agent 處理需要判斷的步驟
- D) 加更多 prompt 說「請務必按照順序執行」

<details><summary>答案</summary>D。光靠 prompt 來約束複雜流程的可靠度很低。A、B、C 都是合理的方向：更強的模型、拆分任務、混合 workflow + agent。</details>
