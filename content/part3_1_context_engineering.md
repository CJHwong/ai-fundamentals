# 3.1 Context Engineering：每個人都需要的技能

## 最重要的一件事

如果你從這整份指南只帶走一個概念，讓那個概念是這個：

**AI 的輸出品質，取決於你給 AI 的 context 品質。**

不是看你用哪個模型，不是看你 prompt 寫得多花俏。是看你提供了什麼資訊、怎麼組織、以及省略了什麼。

這就是 Context Engineering。

## 什麼是 Context

Context 是 LLM 在做預測時能看到的全部資訊，包括：

- 你寫的 prompt / 指令
- 你提供的參考資料
- 對話歷史
- System prompt（系統層級的指令）
- 甚至 AI 自己之前輸出的內容

最後一點很容易被忽略：**AI 自己的輸出也會影響他接下來的輸出。** 如果 AI 在第一輪給了一個錯誤的分析，這個錯誤會留在 context 裡，影響後續的每一輪回答。錯誤會像雪球一樣越滾越大。

## 第一原則：先全部丟進去，再說

現在的 LLM 整理跟過濾資訊的能力已經強到離譜。你不用先幫 AI 篩選、整理、排版。

**起手式就是：把所有你覺得可能相關的東西全部丟進去，加上你的問題，然後看 AI 怎麼回應。**

把整段 Slack thread 貼進去、把整份文件丟進去、把三個相關的 error log 一起貼進去。不用擔心「太多會不會讓 AI 搞混」。現在的模型從大量資訊中抓重點的能力，比大部分人都好。

大部分時候，這樣就夠了。你會得到一個不錯的結果。

**結果不如預期的時候，才需要開始優化 context。** 不要一開始就想太多「該給什麼、不該給什麼」，那是浪費時間。

## 注意：Agent 會先做再說

這件事很重要，所以獨立拉出來講。

**Agent 的預設行為是「行動」，不是「確認」。** 你給他一個模糊的指令，他不會停下來問你「你的意思是 A 還是 B？」。他會直接挑一個方向衝下去，而且表現得很有自信。

這在一開始特別危險。你跟 Agent 還沒建立默契、context 還不完整的時候，他做的每一個假設都可能是錯的。但他不會告訴你他在猜，他會直接執行。

### 為什麼會這樣

LLM 被訓練成「盡量產出有用的回應」。在 LLM 的世界觀裡，不回應 = 沒有幫助。所以他寧可猜一個方向做下去，也不願意停下來說「我不確定」。

這個傾向在 Agent 身上更放大了，因為 Agent 有工具可以用。LLM 猜錯頂多回答不對，Agent 猜錯可能直接改了你的檔案、發了一個 API 請求、或建了一筆錯誤的資料。

### 怎麼應對

**一開始先讓 Agent 只規劃，不執行。**

具體做法：在指令中加上「先告訴我你打算怎麼做，不要直接動手」。等你看過他的計畫、確認方向沒問題之後，再讓他開始執行。

```
❌ 「幫我處理這封客戶的 email」
   → Agent 直接開始做，每一步都在猜你要什麼

✅ 「看一下這封客戶的 email，告訴我你會怎麼處理，列出步驟就好，先不要執行」
   → Agent 列出計畫，你確認後再說「好，照這個做」
```

隨著你跟 Agent 的合作越來越多、context 越來越完整（例如累積了 instruction 文件、過去的處理範例），他的判斷會越來越準。到那時候你可以放手讓他直接執行。

但一開始，永遠是**先看計畫，再放手**。

## 當結果不好時：三個方向排查

如果把所有東西丟進去之後，AI 的輸出仍然不好，通常是以下三個原因之一：

### 1. 關鍵資訊其實不在你給的內容裡

你以為給的夠多了，但 AI 需要的某個關鍵 context 其實不在裡面。例如你問「這個 bug 怎麼修」，貼了 error message，但沒給相關的程式碼或環境設定。

**修法：** 想一下「如果我是一個完全不了解背景的人，看到這些資訊，我能回答這個問題嗎？」缺什麼就補什麼。

### 2. 你的目標不夠明確 (Ambiguity)

你跟 AI 說「幫我改善這個」。改善什麼？效能？可讀性？安全性？UI？AI 不知道，但他不會問你，他會直接猜一個方向做下去。

**修法：** 明確你的目標和限制條件。「改善這個 API 的回應速度，不要改變 response schema」比「改善這個」有用一百倍。

### 3. AI 的前一輪輸出把後面帶歪了

長對話中，如果 AI 在早期輸出了一個錯誤的分析或假設，這個錯誤會留在 context 裡，像雪球一樣越滾越大。

**修法：** 開一個新的對話，把目前的結論摘要帶過去，重新開始。乾淨的 context 比拖著一堆歷史包袱有效得多。

## 寫 Instruction 文件的原則

如果你有在用 AI 工具的 instruction 文件（如 CLAUDE.md、.instructions.md 等），一樣遵守「先全部丟進去」的原則：

1. **先把你知道的都寫進去**：現在的模型（尤其是 Opus 4.6 等級的）消化大量指令的能力很強。不用怕寫太多，先把流程、規則、偏好全部丟進去
2. **發現 AI 開始變笨再整理**：當 instruction 文件大到開始影響 AI 的判斷力（回答品質下降、開始忽略某些規則），就是該整理的時候。把知識拆分成獨立的 skill 或模組，讓 AI 在需要的時候才載入，而不是每次都讀全部
3. **不要只說「不要」，要給替代方案**：寫「不要用 var」沒什麼用，寫「用 const，除非值會改變才用 let」才有用

## 實用技巧

### 避免過早輸出結論

如果你需要分批提供資料給 AI，不要讓 AI 每一批都產出分析。

差的做法：
> 「這是合約的第一部分，請分析重點。」
> → AI 基於不完整的資訊產出分析，這個分析留在 context 裡，影響後續判斷

好的做法：
> 「這是合約的第一部分，請先閱讀但不要分析。如果需要更多資訊，請向我提出問題。全部讀完後我會請你一起分析。」
> → Context 裡不會累積錯誤的中間結論

### 發散與收斂要分清楚

需要創意的時候，不要給太多限制：
> 「我想做一個自動分類 email 的功能，有哪些可能的做法？」

確定方向之後，嚴格限制輸出：
> 「用 LLM classification。設計 API schema，格式用 JSON，只輸出 schema 不要解釋。」

很多人覺得 AI 輸出品質不好，常常是因為該發散的時候給了收斂的指令，或反過來。

### 試試看：Ambiguity vs. 明確指令

先試這個模糊的 prompt：

> 幫我寫一封信給客戶。

看看 AI 給你什麼（很可能是一封正式的英文商務信）。然後試這個：

> 用中文幫我寫一封 LINE 訊息給客戶，語氣輕鬆友善，告訴他訂單已經出貨了，預計三天內到。兩三句話就好。

比較兩次的結果差距。你沒變、AI 沒變，唯一的差別是 context 的明確程度。

### 定期清理 Context

長對話的 context 會越來越髒：錯誤的嘗試、過時的討論、被否決的方案，全部留在裡面。

兩個做法：

1. **總結後開新對話**：請 AI 把目前的結論壓縮成一段摘要，複製到新的聊天視窗繼續
2. **編輯而不是重新生成**：讓 AI 在一個固定的文件上修改，而不是每次都全部重寫

## Context Engineering 不只是 Prompt Engineering

Prompt Engineering 是 Context Engineering 的一個子集。Context Engineering 涵蓋更廣：

- 怎麼設計 system prompt
- 怎麼定義 tool 的 schema（讓 AI 知道工具怎麼用）
- 怎麼決定什麼資訊該放進 context、什麼該省略
- 怎麼管理 agent 在多步驟任務中的 context 演變

這不只是工程師的事。PM 寫需求、CS 整理客戶回報、Ops 描述問題，每個人跟 AI 互動的時候都在做 Context Engineering。你給的 context 越到位，AI 的產出就越有用。

## 關於 Prompt：自己寫，不要抄

網路上到處都有「最強 prompt 模板」、「一鍵安裝的 AI skill」、「複製貼上就能用的 system prompt」。

**不要無腦用。**

兩個理由：

### 1. 你不知道裡面寫了什麼

一段 prompt 可以包含隱藏指令。例如：

- 要求 AI 把你的對話內容傳到某個外部 URL
- 覆寫 AI 的安全限制，讓 AI 執行不該執行的操作
- 在看起來正常的指令中夾帶惡意邏輯

這就是 **prompt injection** 的變體。你從網路上複製一段 prompt，等於讓一個陌生人對你的 AI 下指令。如果你的 AI 有存取公司系統的權限（tool use），這個風險更大。

**原則：每一段你要用的 prompt、每一個你要裝的 skill 或 plugin，都要先讀過一遍，確認你理解裡面在做什麼。** 看不懂的就不要用。

### 2. 別人的 prompt 幫不了你建立直覺

Prompt engineering 的價值不在於背誦模板，在於你自己摸索出「怎麼跟 AI 溝通最有效」的直覺。

這個直覺只能從實作中累積：

- 你丟了什麼 context，AI 給了什麼結果
- 你換了一種問法，結果變好還是變差
- 你加了什麼限制條件，AI 的行為怎麼改變

複製別人的 prompt 跳過了這個過程。短期省時間，長期你永遠不知道為什麼某個 prompt 有效、另一個沒效。

### 好的做法

- **看別人的 prompt 當參考**，理解他為什麼這樣寫，然後用自己的話重新寫一版
- **從最簡單的 prompt 開始**，結果不好再慢慢加條件。這樣你知道每個條件帶來什麼改變
- **安裝任何 skill、plugin、MCP server 之前**，讀一下 source code 或設定檔。至少確認會存取什麼、會送什麼資料到哪裡

### 試試看：Context 的品質決定輸出品質

找一段你最近在處理的工作內容（一封 email、一段 Slack 討論、一份文件），試著用兩種方式問 AI：

第一次，只給最少的資訊：
> 這個問題怎麼解決？[貼上問題描述]

第二次，把完整的背景都丟進去：
> 背景：[貼上相關的對話、文件、錯誤訊息等所有你覺得可能相關的東西]
>
> 問題：[你的問題]
>
> 限制：[有什麼條件或限制]

感受一下兩次回答品質的差距。大部分時候，不是 AI 不夠聰明，是你沒給 AI 夠好的 context。

## Quiz

**Q1.** 你問 AI「這個 bug 怎麼修」，只貼了 error message，AI 給了一個看起來不太對的答案。你的第一步應該是？

- A) 換一個更強的模型
- B) 把 prompt 寫得更詳細
- C) 把相關的程式碼、環境設定一起丟進去
- D) 開一個新對話重問

<details><summary>答案</summary>C。第一原則：先全部丟進去。AI 可能只是缺少關鍵 context。補上相關資訊再看結果，不用急著優化 prompt。</details>

**Q2.** 你需要分三次把一份長合約貼給 AI 分析。以下哪個做法比較好？

- A) 每貼一部分就請 AI 分析重點
- B) 前兩部分請 AI 先讀，最後一部分貼完再一起分析
- C) 三部分各自分析，最後請 AI 合併
- D) 都可以，沒差

<details><summary>答案</summary>B。避免過早輸出結論。如果 AI 在只看到 1/3 的時候就做分析，這個不完整的結論會留在 context 裡，影響後續判斷。</details>

**Q3.** 你跟 AI 討論了 30 分鐘，發現 AI 的回答開始偏離主題、品質下降。最可能的原因和解法？

- A) 模型累了，等一下再問 → 休息一下
- B) 對話太長，context 裡累積了太多雜訊 → 摘要後開新對話
- C) 模型變笨了 → 換一個模型
- D) 你的問題太難了 → 簡化問題

<details><summary>答案</summary>B。長對話中，之前的錯誤嘗試、過時的討論都會留在 context 裡，影響後續輸出。最有效的做法是把結論摘要帶到新對話中重新開始。</details>

**Q4.** 同事分享了一段「超好用的 system prompt」，說是從某個熱門 GitHub repo 複製的。你應該？

- A) 直接用，GitHub 上的東西應該沒問題
- B) 先讀過一遍，確認理解裡面在做什麼再決定要不要用
- C) 只要星星數夠多就可以信任
- D) 請 AI 幫你判斷這段 prompt 安不安全

<details><summary>答案</summary>B。任何外部來源的 prompt 都可能包含隱藏指令（prompt injection）。先讀過、理解裡面在做什麼，看不懂的就不要用。「請 AI 幫你判斷」也不可靠，因為 AI 本身就可能被 prompt injection 繞過。</details>
